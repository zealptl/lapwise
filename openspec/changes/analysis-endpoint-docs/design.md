## Context

The existing v1 wrapper endpoints (meetings, sessions, laps, etc.) each follow a three-part documentation pattern: a `_DESCRIPTION` prose block, a `_RESPONSES` dict with typed examples for 200/422/502/504, and verbose `Query(description=...)` strings. The analysis endpoints were generated by parallel agents who followed the route structure but produced minimal docs. This design describes how to apply the established pattern consistently across all 9 affected files.

## Goals / Non-Goals

**Goals:**
- Every route file has a `_DESCRIPTION` constant with: what the endpoint computes, how the key fields are derived (1–2 sentences, no full algorithm), and any notable defaults or behaviours
- Every route file has a `_RESPONSES` dict with a realistic 200 example, a 422 validation error shape, and the standard 502/504 upstream error shapes
- Every `Query(description=...)` is expanded to match wrapper-endpoint verbosity (e.g. include units, valid range, what "default" means in practice)
- Every route decorator includes `summary=`, `description=_DESCRIPTION`, `responses=_RESPONSES`

**Non-Goals:**
- No behavior changes — this is documentation only
- No changes to models, services, or test files
- No algorithmic documentation in docstrings (belongs in design.md, not HTTP docs)
- No changes to the existing wrapper endpoints

## Decisions

### Decision 1: Follow `meetings.py` as the canonical template exactly

All 9 files will adopt the identical structure to `meetings.py`:
```python
_DESCRIPTION = "..."          # prose string, markdown OK
_200_EXAMPLE = {...}          # realistic payload dict
_RESPONSES = {
    200: {"description": "...", "content": {"application/json": {"example": _200_EXAMPLE}}},
    422: {"description": "...", "model": ErrorEnvelope},
    502: {"description": "...", "content": {...}},
    504: {"description": "...", "content": {...}},
}
@router.get(..., summary="...", description=_DESCRIPTION, responses=_RESPONSES)
```

**Alternative considered:** Inline `description=` strings on the decorator. Rejected — harder to read and edit, inconsistent with wrapper pattern.

### Decision 2: 200 examples use realistic but synthetic values

The analysis endpoints return computed floats (scores, rates, indices). Examples should use plausible values for a recognisable driver (e.g. driver 1 / Verstappen, driver 16 / Leclerc) so they read as meaningful, not as `0.0` / `null` placeholders. Values are not fetched live — they are hand-authored to be representative.

### Decision 3: Field explanations live in `_DESCRIPTION`, not in model `Field(description=...)`

The `Field(description=...)` on Pydantic models already has short descriptions. The `_DESCRIPTION` block adds the *interpretation* layer: what does a `qpace_score` of 80 mean vs 40? This avoids duplication while keeping the route file the single place a developer reads when first encountering the endpoint.

### Decision 4: 502/504 error shapes are shared boilerplate

All endpoints share identical 502/504 shapes (same as wrapper endpoints). Extract as a module-level constant in each file rather than importing a shared dict — keeps each file self-contained and avoids a new shared module for a purely cosmetic change.

## Risks / Trade-offs

- **Synthetic examples go stale** → Low risk; examples are illustrative, not authoritative. A note in `_DESCRIPTION` can point to the live API for real values.
- **Verbosity increases file size** → Acceptable trade-off. Wrapper endpoints are already ~150 lines; analysis routes will be similar.

## Open Questions

None — pattern is established, scope is bounded.
